# Stage 18 — BE-016 Notes Implementation Plan

**Status:** Backend implementation and all required Windows gates complete. Ready for commit and FE-019/FE-020 stage18 handoff.

**Goal:** Deliver durable Notes commands, revision-safe autosave, lifecycle operations, public search and maintenance APIs, real BE-010 integration, and BE-012 backup v2/import/reset on Windows.

**Completion Criteria:** Migration 7 upgrades and reopens safely; all documented command/error/event contracts are executable; concurrent edits cannot overwrite newer revisions; Active/Archive/Trash queries are deterministic; Search excludes Trash; v1 import preserves Notes and v2 merges Notes atomically with other owners; generated contracts and all final gates pass. Backend completion is a handoff to FE-019/FE-020 Home and aggregate integrations, not completion of all stage18.

**Architecture:** Notes owns its SQLite rows and business rules. App composition adapts public Notes records to Search and Data Management. Reuse the existing shared maintenance gate; coordinator-owned transactions call owner `_in` APIs without nested locks or Storage access.

**Tech Stack:** Existing locked Rust/Tauri/rusqlite/Serde/ts-rs/Tokio/UUID dependencies and existing frontend verification tools. No new dependency or version change.

## Scope

**In scope:** All BE-016 commands/DTOs/errors/event, migration, persistence, blocking work, Notes public search and transaction maintenance APIs; BE-010 Note document/source/DTO variants and adapter; BE-012 strict backup v2, v1 compatibility, preview/counts/merge/reset/rollback/publication; app registration and generated bindings. A minimal existing Search UI guard is necessary for the new generated target union before the FE owner arrives.

**Out of scope:** Notes frontend feature source, Home composer and aggregate rendering, FE autosave debounce, Markdown rendering, floating Quick Note window, global shortcut/tray integration, Calendar, new dependencies, historical plan edits, commits, shutdown, automated desktop E2E and macOS validation.

## Global Constraints

- Rust owns persistence and business rules; frontend communication uses narrowly scoped real Tauri commands/events. Roadmap stage18 takes precedence over the obsolete generic mock-IPC sentence in PLANS.md.
- Every function, method, callback, helper and test has a short English purpose comment. Markdown is UTF-8.
- Generated bindings are generated from Rust and never hand edited.
- Only Windows build/test during development. Do not add or run automated desktop end-to-end tests.
- Do not log note content/title/snippet/query/project identifiers or backup data.
- Preserve migrations 1–6 and existing capability boundaries. No new permission, OS file access, background purge or sample Notes.

## Assumptions, Risks, and Blockers

**Assumptions:** BE015 `31e324c` and FE018 `f0cb7ee` are the handed-off baseline. User authorizes resolving contract mismatches and recording the decisions in BE-016. Existing dependencies suffice. Backend construction prepares `quick-note` caller authorization only; no stage19 window is created.

**Risks:** Unicode lowercasing expands scalars; snippets/highlights must map display offsets. Backup import must not mutate parsed records or deadlock by reentering the gate. Project removal uses FK unlink without a Notes revision/event, so FE must later refresh on canonical Projects removal events. Search target union requires explicit narrowing in the current UI. Each risk has tests below.

**Blockers:** None for backend implementation. Native UI/UNC validation inherited from stage17 remains unverified because native control was unavailable; do not relabel this as a passed gate. This plan introduces no native-only Notes behavior. Stage18 FE acceptance remains pending its subsequent design/plan/implementation.
