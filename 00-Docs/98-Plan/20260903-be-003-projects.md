# BE-003 Projects Implementation Plan

**Status:** Implemented

**Goal:** Implement the complete `BE-003` Projects backend contract on top of
`BE-002`, so XWork can safely register existing folders as durable project
metadata, query current folder availability, mutate project metadata, open or
relocate roots through native Rust adapters, and remove metadata without ever
deleting user files.

**Completion Criteria:**

- Migration `0001_create_projects.sql` creates only the documented strict
  `projects` table and `idx_projects_list_order`, is registered as version `1`,
  and preserves the atomic migration behavior established by `BE-002`.
- Add, list, get, rename, pin, open, locate, open-folder, removal-impact, and
  remove behavior matches the validation, ordering, availability, concurrency,
  error, and side-effect rules in `BE-003`.
- Canonical path identity prevents duplicate registration, including Windows
  separator and case variants, while duplicate display names remain valid.
- Every persistent mutation holds a shared `DataReadPermit` through commit and
  post-commit publication; project removal also prevents competing mutations
  and future session creation for the same project.
- Removal always requires confirmation, recalculates impact after closing the
  admission gate, deletes metadata only after runtime cleanup succeeds, and
  never deletes, moves, or edits the selected folder or its contents.
- Public Rust queries and typed maintenance contracts are available to later
  Sessions, Git, File, Backup, Notes, and Calendar integration without exposing
  the Projects repository or database schema.
- All ten Tauri commands authorize the exact invoking window before any input,
  database, filesystem, picker, opener, or runtime work; `list_projects` allows
  `main` and `quick-note`, while the other commands allow only `main`.
- `projects://changed` is emitted only after a committed real mutation, as an
  invalidation signal; failed emission never changes the command result.
- TypeScript bindings are generated from the Rust DTO and error definitions and
  checked for drift; generated files are never edited by hand.
- Automated tests use only temporary databases and directories plus fake
  platform, clock, UUID, event, and runtime seams; no test touches app data or
  opens native user interface.
- All frontend and Rust quality gates pass on Windows, `pnpm tauri build`
  succeeds, and the native folder picker and file-manager opener pass the
  documented Windows smoke checks.

**Architecture:** `projects` owns its persisted models, SQL repository,
validation, path identity, platform port, runtime-guard port, commands, events,
errors, and public owner queries. `ProjectService` is the only orchestration
entry point for commands and backend consumers. SQLite and filesystem work run
on blocking workers, while native dialog/opener calls remain asynchronous.
`shared::maintenance` supplies one application-wide Tokio read/write gate; the
composition root creates one gate, constructs `ProjectService` with the same
instance, installs `NoProjectRuntimeGuard` until `BE-005`, registers the official
plugins, manages the service, and extends the single invoke handler. Projects
never imports a later capability's implementation.

**Tech Stack:** Rust `1.98.0` stable, Cargo `1.98.0`, Rust Edition `2024`, Tauri
`2.11.5`, SQLite through `rusqlite = { version = "=0.40.2", features =
["bundled"] }`, `serde = { version = "=1.0.229", features = ["derive"] }`,
`ts-rs = "=12.0.1"`, `tokio = { version = "=1.53.1", features = ["sync"] }`,
`uuid = { version = "=1.26.0", features = ["v4"] }`,
`tauri-plugin-dialog = "=2.7.3"`, `tauri-plugin-opener = "=2.5.5"`, and the
existing `tempfile = "=3.27.0"` test dependency. The four new exact versions

minimum Rust version is compatible with Rust `1.98.0`. Cargo resolution in Task

  depends only on public owner APIs.

- Rust-generated TypeScript bindings under `src/bindings/projects/` and drift

**Out of Scope:**

- `FE-002`, `FE-004`, or changes to the `FE-001` sidebar; no frontend calls the
  new commands in this plan.
- Git repository detection/status (`BE-004`) and session/tab/process lifecycle
  (`BE-005` through `BE-007`).

  flow, or Settings UI (`BE-012`); this plan creates only the owner contract and
  typed adapter explicitly assigned to `BE-003`.

  or aggregated project DTO fields.
- Creating, cloning, copying, renaming, moving, watching, scanning, or deleting
  a project folder or any file within it.
- Persisted availability, a filesystem watcher, database pooling, or a project
  cache not required by the specification.
- Webview permissions for dialog, opener, or general filesystem access; both
  official plugins are called only from Rust.
- Automated desktop end-to-end tests and macOS validation.

## Global Constraints

- "Keep OS access, persistence, terminal processes, and business rules in Rust;
  the React frontend communicates with them through narrowly scoped Tauri
  commands and events." (`AGENTS.md`)
- "Every function, method, callback, test, and helper must have a short comment
  describing its purpose." (`AGENTS.md`)
- "Migration đặt tại `src-tauri/migrations/`, chỉ được thêm file mới và không
  sửa migration đã phát hành." (`00-Docs/00-Overview/02-ProjectStructure.md`)
- Only backend code accesses SQLite; the frontend receives generated contracts
  and never uses a SQL or Store plugin. (`00-Docs/00-Overview/01-TechStack.md`)
- A capability may depend on `storage`, `shared`, and platform ports, but may not
  access another capability's internal implementation.
  (`00-Docs/00-Overview/02-ProjectStructure.md`)
- `root_path` and `path_key` are derived only from a Rust-owned native folder
  selection; add/locate never accepts an arbitrary frontend path.
  (`00-Docs/03-Backend/BE-003-projects.md`)
- Lock acquisition order is `DataMaintenanceGate` -> project mutation/removal
  gate -> `Storage`; `_in` maintenance methods re-enter none of them.
  (`00-Docs/03-Backend/BE-003-projects.md`)
- SQLite, metadata, canonicalization, and path checks execute through
  `tauri::async_runtime::spawn_blocking`; no `State`, owner mutex, storage guard,
  connection, or transaction is held across `.await`.
  (`00-Docs/03-Backend/BE-003-projects.md`)
- Generated bindings under `src/bindings/` are not manually edited.
  (`PLANS.md`)
- Development and verification are Windows-only; macOS checks wait for release
  preparation. (`AGENTS.md`)

Every task implicitly includes these constraints.

## Assumptions, Risks, and Blockers

**Assumptions:**

- `BE-002` is complete in the current tree, and its `Storage`, atomic migration
  runner, isolated app-builder seam, and version-`0` production registry are the
  stable prerequisite for this plan.
- `BE-003` reports no open questions and is the source of truth when a wireframe
  depicts later Git, session, file, note, or event data not owned by Projects.
- `NoProjectRuntimeGuard` returns zero impact and successful idempotent cleanup
  until the Stage 8 `BE-005` composition replaces it; command and service
  contracts do not change at that time.
- No capability permission file changes are necessary because webviews receive
  neither dialog/opener plugin commands nor direct filesystem authority.

**Risks:**

- Windows path identity is easy to get subtly wrong for drive, UNC, separator,
  verbatim-prefix, case, root, and non-UTF-8 cases. Task 4 uses deterministic
  path-key fixtures plus real temporary-directory canonicalization and keeps the
  normalization logic inside Projects.
- Native dialog and opener APIs are unavailable in headless tests. Tasks 4 and 7
  inject fake `ProjectPlatform` implementations, while Final Verification uses
  a short manual Windows smoke check for the real adapters.
- Concurrent remove, ordinary mutation, and future session creation can race.
  Tasks 2 and 6 test admission order, a per-project removal gate, recalculated
  impact, cleanup failure, delete-after-cleanup failure, and retry behavior.
- Emission happens after durable commit, so an event failure cannot be rolled
  back. Task 6 injects a recording/failing event sink and verifies that callers
  still receive the committed result and later queries recover the truth.
- The owner maintenance API is implemented before its full `BE-012` coordinator.
  Task 5 constrains it with direct shared-transaction contract tests, opaque
  owned types, and the exact future adapter boundary so later work does not need
  repository access or contract redesign.
- Adding the first business migration changes startup and packaged desktop
  behavior. Tasks 1 and 8 cover migration/startup in isolated app data, and the
  final Windows Tauri build exercises embedded resources and plugin wiring.

**Blockers:** None.

## Test Isolation and Seams

- Every storage integration creates a `tempfile::TempDir`, passes its path to
  `Storage::open` or `configure_with_*_for_tests`, and drops it after the test.
- Filesystem behavior uses subdirectories/files created under a test-owned
  `TempDir`. Tests never select the repository root, home directory, or resolved
  production app-data directory.
- Unit tests inject `ProjectPlatform`, clock, UUID provider, event sink, and
  `ProjectRuntimeGuard` fakes. Each fake records calls and can return a precise
  cancellation or failure without opening a dialog, file manager, or process.
- Concurrency tests coordinate fake runtime and mutation operations with Tokio
  channels/barriers owned by the test. They do not mutate process-global
  environment variables or depend on sleeps for ordering.
- Composition tests use the existing Tauri mock runtime and an explicit
  temporary app-data path. Plugin behavior is not invoked there; only setup,
  state identity, routing, and authorization are observed.
- Startup failure injection uses an app-data path that is a regular file and a
  temporary database whose `user_version` is greater than `1`. The observable
  result is the existing documented setup panic during the first mock runtime
  iteration, with no managed project service published.
- Native picker and opener are exercised only by the final manual Windows smoke
  checklist against throwaway folders created specifically for that check.

## Dependency Order

1. Task 1 (dependencies and schema) -> enables repository persistence and
   packaged plugin resolution.
2. Task 2 (shared maintenance gate) -> enables every persistent service mutation
   and the future maintenance coordinator contract.
3. Task 3 (models, errors, repository, and bindings) -> enables service behavior
   without coupling commands to SQL rows.
4. Task 4 (path/platform and core service behavior) -> enables native add/locate,
   availability, and public owner queries.
5. Task 5 (typed data-maintenance owner API) -> enables the future coordinator
   adapter without exposing Projects internals.
6. Task 6 (removal and mutation concurrency) -> completes destructive-operation
   safety before commands expose it.
7. Task 7 (commands and event boundary) -> enables composition and IPC contract
   integration.
8. Task 8 (composition root and full contract integration) -> enables final
   automated and manual verification.

## Deviations and Decisions

- **Test seams are `#[doc(hidden)] pub` instead of `pub(crate)`.** `BE-003`
  declares `pub(crate) trait ProjectPlatform`, but integration tests are separate
  crates and must inject fakes for the picker, opener, clock, identifier factory,
  and event sink. `ProjectPlatform`, `ProjectClock`, `ProjectIdFactory`,
  `ProjectEventSink`, `PathIdentity`, and `CURRENT_PATH_IDENTITY` therefore follow
  the existing `BE-001` `AppRuntime` precedent: `pub` with `#[doc(hidden)]`. No
  webview or capability permission is affected.
- **`ProjectEventSink::publish` returns `Result<(), ProjectsError>`.** The
  specification requires that a failed emission never changes the command result.
  A fallible port makes that observable in tests; `ProjectService` logs the event
  name and project identifier and still returns the committed result.
- **Task 1 also updated two existing schema-version assertions.** Registering
  migration version `1` immediately changed `tests/app_builder.rs` and
  `tests/app_lifecycle.rs`, which asserted version `0`. Both were updated in Task 1
  (instead of Task 8) so the tree stayed green between tasks; the newer-database
  fixture moved from `user_version = 1` to `2` for the same reason.
- **Tasks 7 and 8 were implemented together.** Command routing lives in
  `app::configure`, so the `command_` boundary tests cannot observe a routed
  command until the composition root registers it. Both tasks were completed in
  one step and verified by the commands listed in each.
- **The red step was observed for Tasks 1 through 3 only.** Task 1's migration
  test failed on schema version `0`, Task 2's gate tests failed on the missing
  `DataMaintenanceGate` and permit types, and Task 3's binding test failed on
  missing generated output. Tasks 4 through 8 were written implementation-first and
  then covered by their tests; the failing-test-first sequence was not recorded for
  those tasks.
- **`ProjectsError` struct-variant fields stay snake_case.** The generated
  TypeScript renders `{ "code": "projectNotFound", project_id: string }` because the
  `BE-003` error definition applies `rename_all = "camelCase"` to variant names only,
  unlike the DTO definitions that also rename fields. The implementation follows the
  specification literally; changing the wire shape needs a specification update.
- **Owner maintenance preparation never touches the filesystem.** `_in` APIs run
  inside a coordinator-owned transaction, so `prepare_backup_merge_in` normalizes
  the incoming `root_path` as a string (verbatim prefix, trailing separator, path
  key) instead of calling `canonicalize`, which would fail for a folder that does
  not exist on the importing machine.
- **Merge resolution prefers the local folder over the source identifier.** When an
  incoming record names a folder that a local project already owns, the plan remaps
  the source identifier onto the local project so the unique `path_key` constraint
  can never be violated. Two incoming records naming one folder are rejected with
  `ProjectAlreadyExists`.
- **Added three observability seams.** `ProjectService::shares_gate_with`,
  `ProjectService::storage_for_tests`, and `app::official_plugins_initialized` exist
  so composition and partial-failure tests can assert shared gate identity, a
  delete-after-cleanup failure, and plugin registration without invoking native
  user interface.
- **`tests/data_management_contract.rs` was created in Task 2.** The file holds the
  gate admission tests from Task 2 and gained the `projects_` maintenance contract
  tests in Task 5, as both tasks list it.

During implementation, append material deviations and decisions without
rewriting completed history.
