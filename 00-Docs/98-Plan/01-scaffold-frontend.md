# Phase 1 — Frontend Scaffold Implementation Plan

**Status:** Draft

**Goal:** Create a minimal client-only SPA that runs with Vite, renders an empty
application shell through a memory router, and has complete frontend quality
gates that run both locally on Windows and in GitHub Actions.

**Completion Criteria:**

- `pnpm dev` starts the SPA, and route `/` renders an empty application shell
  without behavior from any `FE-NNN` feature.
- React Router uses a memory router, and a component test proves that route `/`
  renders the correct shell.
- Tailwind CSS 4, source aliases, and `components.json` are ready for adding
  shadcn/ui or Animate UI source components during feature implementation; no
  component is added in advance.
- Every direct frontend dependency is pinned to an exact version in
  `package.json`, `pnpm-lock.yaml` is committed, and the Node.js and pnpm
  versions are pinned according to the tech stack.
- The formatter check, lint, type check, unit/component tests, and production
  build all pass locally on Windows.
- A GitHub Actions workflow runs the same frontend quality gates on Windows and
  completes successfully.

**Architecture:** `src/main.tsx` only initializes React and mounts the
`RouterProvider` supplied by `src/app/`. The composition root remains in
`src/app/`; no feature, IPC wrapper, generated binding, or backend is created.
The router uses in-memory history so the same frontend can run under Vite in
this phase and be wrapped by Tauri in Phase 6 without depending on browser URLs.

**Tech Stack:** Node.js 24 LTS, pnpm 11.25.0, TypeScript 7.0.2, React 19.2.8,
Vite 8.2.2, Tailwind CSS 4.3.3, React Router 8.3.1, Zustand 5.0.15, Biome
2.5.11, Vitest 4.1.11, and React Testing Library 16.3.3.

**Sources:**

- Roadmap: `00-Docs/98-Plan/00-Roadmap.md`, Phase 1 frontend scaffold section
- Tech stack: `00-Docs/00-Overview/01-TechStack.md`
- Project structure: `00-Docs/00-Overview/02-ProjectStructure.md`
- Product scope and interaction constraints:
  `00-Docs/00-Overview/03-FunctionalRequirements.md`, sections 1 and 18
- Plan rules: `PLANS.md`

No `FE-NNN` specification, `BE-NNN` specification, or wireframe applies to this
plan because the scaffold does not implement a product feature or interface.

## Scope

**In Scope:**

- A frontend manifest and lockfile with the correct runtime, package manager,
  and target versions for Phase 1.
- Vite, React, TypeScript, and Tailwind CSS 4 configuration, including an `@/*`
  alias that maps to `src/*`.
- A memory router, entry point, and empty application shell at route `/`.
- React Router and Zustand installed as required by the roadmap; Zustand remains
  unused until real UI state exists.
- Registry-compatible infrastructure for shadcn/ui and Animate UI through
  `components.json`, aliases, and Tailwind; source components are added only
  when a feature-phase consumer exists.
- Biome, `tsc --noEmit`, Vitest, React Testing Library, and a minimal component
  test for the router and shell.
- Consistent npm scripts for development, build, and quality gates.
- GitHub Actions running the frontend quality gates on Windows.
- Ignore rules only for `node_modules/` and the production bundle created by
  Phase 1.

**Out of Scope:**

- Any behavior, layout, design token, or UI state from `FE-001` through
  `FE-023`.
- Mock IPC, temporary DTOs, `src/lib/ipc/`, and sample data; these begin when
  their corresponding features are implemented.
- shadcn/ui or Animate UI source components, Motion, Lucide React, forms, panes,
  editors, terminals, or feature-specific dependencies.
- Feature directories under `src/features/`, `src/bindings/`, and shared helpers
  without a consumer.
- Tauri, `src-tauri/`, the Rust toolchain, capabilities, desktop integration,
  and Tauri builds; these belong to Phase 6.
- Desktop E2E tests and macOS validation.
- The design or implementation of the complete application shell specified by
  `FE-001`.

## Global Constraints

- Run as a client-only SPA without SSR or React Server Components.
- React Router must use a memory router and must not depend on browser history
  or server routes.
- Tailwind CSS 4 must use CSS-first configuration without a CSS preprocessor.
- TypeScript performs type checking only; Vite performs transpilation and
  bundling.
- Use Biome instead of ESLint; do not retain ESLint configuration generated by
  a Vite template.
- Pin Node.js 24 LTS with `engines` and pnpm 11.25.0 with `packageManager`; pin
  every direct frontend dependency to an exact version and commit
  `pnpm-lock.yaml`.
- Do not install a dependency merely because it appears in the tech stack; only
  dependencies required by the scaffold are allowed in the manifest.
- Add shadcn/ui and Animate UI components as repository-owned source only when
  they begin to be used, and do not automatically synchronize them with
  upstream.
- The frontend must not directly access the filesystem, database, shell, child
  processes, or credential store.
- `src/app/` contains only the composition root, router, providers, and
  application-level shell; it must not contain business rules or
  feature-specific implementation.
- Do not create empty directories or `.gitkeep` files to reproduce the complete
  target tree. `src/features/<feature>/`, `src/components/`, `src/lib/`, and
  `src/assets/` appear only when they contain a real file with the corresponding
  responsibility.
- Frontend files use `kebab-case`, components use `PascalCase`, and tests are
  colocated with their source and use the `.test.tsx` suffix.
- Every added function, callback, test, and helper must have a short purpose
  comment that does not restate obvious behavior.
- Validate only on Windows during this development phase; defer macOS validation
  until release preparation.

## Assumptions, Risks, and Blockers

**Assumptions:**

- “Empty application shell” means a minimal semantic root with the application
  name for render verification, not the sidebar, top bar, navigation, or layout
  from `FE-001`.
- `react-dom` uses React's 19.2.8 version, and the Tailwind plugin for Vite uses
  the same 4.3.3 release line as Tailwind CSS.
- Required support packages for which the documentation does not specify an
  individual version, such as React/Vite plugins, type packages, the DOM test
  environment, and jest-dom matchers, are selected at versions compatible with
  the target versions, installed with `--save-exact`, and locked in
  `pnpm-lock.yaml`.
- Animate UI uses shadcn-compatible registry infrastructure; it needs no runtime
  package or source component before a component is selected.

**Risks:**

- The Vite generator may add ESLint, sample assets, or structure that does not
  belong to XWork. Task 1 mitigates this by creating a minimal manifest, and
  Task 2 creates only the listed files without retaining demo scaffold content.
- Support packages without documented versions may be incompatible with
  TypeScript 7 or Vite 8. Task 1 verifies peer dependencies, pins exact
  versions, and stops on a pnpm peer mismatch instead of applying an arbitrary
  override.
- Registry configuration could accidentally add unused components or
  dependencies. Task 2 creates only `components.json` and verifies that the diff
  contains no source component.
- Local and CI quality gates could diverge. Task 3 invokes the same scripts that
  passed locally, uses the same Node.js and pnpm versions, and installs with
  `--frozen-lockfile` on Windows.

**Blockers:** None.

Do not begin implementation if resolving a peer dependency requires changing a
target version in the tech stack. Update the documented decision first.

## Dependency Order

1. Task 1 pins the runtime, dependencies, and script contract → enables the
   Task 2 source and tools to run in a reproducible environment.
2. Task 2 creates the SPA, router, UI registry infrastructure, and tests →
   produces every local quality gate that CI will invoke.
3. Task 3 runs those quality gates in Windows GitHub Actions → proves that the
   scaffold can be verified outside the development machine.

### Task 1: Pin the Minimal Frontend Toolchain and Dependencies

**Outcome:** A minimal frontend manifest that pnpm can install reproducibly,
contains only Phase 1 dependencies, and provides a shared script contract for
local development and CI.

**Depends On:** None

**Files:**

- Create: `package.json`
- Create: `pnpm-lock.yaml`
- Modify: `.gitignore`

**Interfaces:**

- Consumes: Node.js 24 LTS, pnpm 11.25.0, and the target versions in
  `00-Docs/00-Overview/01-TechStack.md`.
- Produces: the `dev`, `build`, `format`, `format:check`, `lint`, `typecheck`,
  `test`, and `test:watch` scripts; the `pnpm@11.25.0` package-manager alias; an
  exact dependency graph and lockfile used by Tasks 2–3.

- [ ] **Step 1: Create the minimal manifest and pin the environment**

  Create a private ESM package, declare `engines.node` for Node.js 24 LTS, and
  set `packageManager` to `pnpm@11.25.0`. Define the scripts above with direct
  Vite, Biome, TypeScript, and Vitest commands; do not hide any quality gate
  behind a combined script.

- [ ] **Step 2: Install the correct scaffold dependencies with exact versions**

  Runtime dependencies include only React/React DOM, React Router, and Zustand.
  Development dependencies include only TypeScript, Vite and its React plugin,
  Tailwind CSS and its Vite plugin, Biome, Vitest, jsdom, React Testing Library,
  jest-dom matchers, and the type packages needed to compile configuration and
  source files.

  Use `pnpm add --save-exact` or `pnpm add --save-dev --save-exact`. Do not
  install the shadcn CLI, Animate UI components, Motion, Lucide, Tauri, or any
  feature dependency. Do not use `--force`, `--legacy-peer-deps`, or overrides
  to hide a peer mismatch.

- [ ] **Step 3: Create the lockfile and ignore frontend artifacts**

  Generate `pnpm-lock.yaml`. Add `node_modules/` and `dist/` to `.gitignore`;
  preserve the existing ignore rules and do not add unrelated patterns.

- [ ] **Step 4: Verify the dependency contract**

  Run: `pnpm install --frozen-lockfile`

  Expected: installation succeeds, the lockfile remains unchanged, and no peer
  dependency warning or error appears.

  Run: `pnpm list --depth 0`

  Expected: only direct scaffold dependencies are present, target versions
  match the tech stack, and every direct dependency uses an exact version in
  `package.json`.

### Task 2: Create the SPA, Memory Router, and Local Quality Gates

**Outcome:** Route `/` renders an empty application shell under Vite, and the
router/shell test, Tailwind, TypeScript, Biome, and production build all work
without feature code.

**Depends On:** Task 1

**Files:**

- Create: `index.html`
- Create: `tsconfig.json`
- Create: `vite.config.ts`
- Create: `biome.json`
- Create: `components.json`
- Create: `src/main.tsx`
- Create: `src/vite-env.d.ts`
- Create: `src/index.css`
- Create: `src/app/app-shell.tsx`
- Create: `src/app/app-router.tsx`
- Test: `src/app/app-router.test.tsx`

**Interfaces:**

- Consumes: package scripts and the dependency graph from Task 1.
- Produces: the TypeScript/Vite alias `@/*` → `src/*`; an `AppShell` component
  with no props; a `createAppRouter(initialEntries?: string[])` factory that
  returns a memory router; route `/`; and shadcn aliases for `components`, `ui`,
  `lib`, and `utils` so the registry can add source to the correct area in a
  later phase.

- [ ] **Step 1: Write the root-route component test before implementation**

  Create a colocated test that initializes the router with entry `/`, renders
  it through `RouterProvider`, and asserts that the minimal application shell
  has the accessible name “XWork”. Declare jsdom at file level so the red test
  does not depend on configuration that has not yet been created. Place short
  comments above the test callback and cleanup callback as required by the
  repository comment rules.

- [ ] **Step 2: Verify that the test fails because the router is absent**

  Run: `pnpm test -- src/app/app-router.test.tsx`

  Expected: the test fails because `src/app/app-router.tsx` does not exist; the
  failure must not come from a missing dependency or test-environment
  configuration.

- [ ] **Step 3: Configure the minimal frontend**

  Configure strict TypeScript, `noEmit`, React's JSX transform, and the `@/*`
  alias. Configure Vite with React, Tailwind CSS 4, the matching alias, and
  Vitest with jsdom. Configure Biome for repository source and configuration
  files without formatting generated artifacts. `src/index.css` imports only
  Tailwind; do not add feature design tokens or themes to the scaffold.

- [ ] **Step 4: Establish shadcn/ui and Animate UI infrastructure without a component**

  Create `components.json` using the current schema, the `src/index.css` CSS
  entry, Tailwind CSS 4 CSS variables, and aliases that point to the target tree
  under `src/`. Do not run a component-add command, create empty
  `src/components/ui/` or `src/components/animate-ui/` directories, or create a
  `cn` helper without a consumer.

- [ ] **Step 5: Implement the entry point, memory router, and minimal shell**

  `src/main.tsx` mounts React strict mode and `RouterProvider` into the root from
  `index.html`. `createAppRouter` registers only route `/` with `AppShell`; its
  `initialEntries` parameter lets the test control the initial location without
  changing production behavior. `AppShell` renders only a semantic shell named
  “XWork”; do not add a sidebar, top bar, links, a store, or business state.

- [ ] **Step 6: Verify the focused test and local quality gates**

  Run: `pnpm test -- src/app/app-router.test.tsx`

  Expected: the route `/` test passes without unhandled React or Router
  warnings.

  Run: `pnpm format:check`

  Expected: no file requires formatting.

  Run: `pnpm lint`

  Expected: the command passes without diagnostics.

  Run: `pnpm typecheck`

  Expected: the command passes without type errors or emitted output.

  Run: `pnpm test`

  Expected: all frontend tests pass and the process exits with code 0.

  Run: `pnpm build`

  Expected: Vite creates the production bundle in `dist/` without a build
  error.

- [ ] **Step 7: Smoke-test the development server on Windows**

  Run: `pnpm dev`

  Expected: Vite prints a local URL, opening it renders the “XWork” shell, the
  browser console contains no errors, and stopping the development server
  leaves no background process.

  Inspect the diff after the smoke test: it must contain no shadcn/ui or Animate
  UI source component, feature directory, IPC wrapper, generated binding, or
  Tauri file.

### Task 3: Add Frontend CI on Windows

**Outcome:** GitHub Actions installs the exact lockfile and automatically blocks
frontend changes that fail formatting, linting, type checking, tests, or the
production build.

**Depends On:** Task 2

**Files:**

- Create: `.github/workflows/frontend-ci.yml`

**Interfaces:**

- Consumes: `packageManager`, `engines`, `pnpm-lock.yaml`, and the
  `format:check`, `lint`, `typecheck`, `test`, and `build` scripts from Tasks
  1–2.
- Produces: the Windows `frontend-ci` workflow and one frontend quality-gate
  job.

- [ ] **Step 1: Create the minimal Windows workflow**

  Run on `windows-latest` for `push` and `pull_request`. Check out the source,
  install pnpm 11.25.0, install Node.js 24 with pnpm caching, run
  `pnpm install --frozen-lockfile`, then run the format check, lint, type check,
  tests, and production build in order. Do not add a macOS matrix, Rust, Tauri,
  artifact publication, or deployment.

- [ ] **Step 2: Verify that the workflow uses the local contract**

  Review the YAML to ensure it does not duplicate commands that differ from the
  `package.json` scripts, use `continue-on-error` for a quality gate, or request
  unnecessary write permissions or secrets.

  Run: `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build`

  Expected: the local command sequence corresponding to the CI job passes on
  Windows.

- [ ] **Step 3: Verify the GitHub Actions run**

  After the change is available on GitHub, observe the `frontend-ci` workflow.

  Expected: the Windows job completes successfully from a clean checkout with
  `--frozen-lockfile`; it contains no macOS, Rust, or Tauri step.

configuration, or Tauri bundling.
